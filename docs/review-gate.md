# 리뷰 게이트 (코드 리뷰 코멘트 기반 병합 차단)

PR을 올리면 AGENTS.md 지침에 따라 에이전트가 `.agents/skills/code-review/SKILL.md` 기준으로 **자동으로 리뷰하고 PR 리뷰 코멘트를 남긴다.** 병합 가능 여부는 승인할 사람이 아니라 **그 코멘트의 내용**으로 정한다. 별도 AI 리뷰 워크플로나 API 키는 쓰지 않는다.

## 규칙
| 최신 커밋의 리뷰 코멘트 | `check` | 병합 |
|---|---|---|
| 없음(또는 이전 커밋에 대한 리뷰뿐) | 실패 | 불가 |
| `[치명]` 또는 `[중요]` 지적이 있음 / 판정 `수정 필요` | 실패 | 불가 |
| 제안만 있음, 판정 `승인` | 통과 | 가능 |
- 게이트는 CI의 `check` job 안의 한 단계(`Review gate`)다. 필수 체크는 기존 `check` 하나뿐이다(새 필수 체크 없음).
- 새 커밋을 푸시하면 이전 리뷰는 무효가 된다. 새 HEAD 기준으로 리뷰를 다시 남겨야 통과한다.
- 리뷰는 CI가 끝난 뒤에 남으므로, 리뷰를 남긴 다음 **같은 PR의 `check` 실행을 다시 돌려** 게이트를 재평가한다. `.github/scripts/post-review.sh <PR번호> <본문 파일>`이 리뷰 게시와 재실행을 함께 한다.
  - 리뷰 이벤트(`pull_request_review`)로 별도 실행을 만드는 방식은 쓰지 않는다. 같은 이름의 `check`가 한 커밋에 여러 개 쌓이면 먼저 실패한 실행이 병합 판정에 남아, 나중 실행이 성공해도 PR이 계속 BLOCKED였다(실제로 확인).

## 리뷰로 인정되는 조건 (`.github/scripts/review-gate.sh`)
- 저장소 쓰기 권한자가 남긴 리뷰: `author_association`이 OWNER·MEMBER·COLLABORATOR이거나, 같은 저장소 브랜치에서 올린 PR의 작성자 본인(같은 저장소 브랜치에 푸시하려면 쓰기 권한이 필요하다). 비공개 조직 멤버는 Actions 토큰에서 association이 낮게 보일 수 있어 후자를 함께 인정한다. 포크 PR은 후자가 적용되지 않는다.
- 본문에 마커 `<!-- code-review -->`가 있고, 리뷰가 달린 커밋이 PR HEAD와 같다.
- `판정:` 줄이 있다(완성되지 않은 리뷰는 인정하지 않음).
- 지적 줄은 `- [치명]`, `- [중요]`, `- [제안]`으로 시작한다. 형식은 스킬의 보고 형식을 따른다.
- 같은 HEAD에 리뷰가 여러 개면 가장 최근 제출분만 본다.

## 흐름
1. PR 생성 → 게이트 실패(리뷰 없음, 정상).
2. 에이전트가 `post-review.sh`로 리뷰를 남기고 `check`를 재실행 → 게이트 재평가.
3. 치명·중요가 있으면 수정 → 푸시 → 다시 리뷰 → 통과 후 병합.

## 한계
- 코멘트가 에이전트가 쓴 것인지 사람이 쓴 것인지는 구분하지 못한다. 쓰기 권한자의 리뷰면 인정하므로, 혼자 쓰는 저장소에서는 본인이 직접 `판정: 승인` 리뷰를 달아 우회할 수 있다. 신뢰 모델은 "리뷰를 거치는 절차를 강제"하는 수준이다.
- 리뷰 품질은 에이전트의 판단에 달려 있고 오탐·누락이 있을 수 있다.
- 리뷰를 남길 때마다 `check`를 재실행하므로 CI 시간이 든다. 재실행을 잊으면 게이트가 이전 결과(리뷰 없음)로 남아 병합이 막힌다.
- 리뷰를 남기는 계정이 PR 작성자와 같아도 `COMMENTED` 리뷰는 허용된다(승인·변경 요청 상태는 본인 PR에 불가).

## 로컬 시험
`REVIEWS_FILE=<reviews JSON 배열> HEAD_SHA=<sha> bash .github/scripts/review-gate.sh`
