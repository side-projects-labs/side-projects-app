# 공통 리뷰 기준

1. 변경 범위를 파악한다: `git diff origin/master...HEAD`, 연결된 이슈(`Refs #`)의 완료 기준과 대조한다. 요청 범위를 벗어난 변경이 섞였으면 분리를 제안한다.
2. **병합 조건**: CI의 `check`가 통과해야 한다. `check`에는 타입 체크, lint, 테스트와 **리뷰 게이트**가 들어 있다. 게이트는 PR **최신 커밋**에 남긴 이 리뷰 코멘트를 읽어, `[치명]`·`[중요]` 지적이 있거나 리뷰가 없으면 병합을 차단한다(`docs/review-gate.md`). 따라서 아래 **보고 형식과 마커를 정확히 지켜야** 한다.
3. 지적은 **실제로 읽고 확인한 코드**에 한정한다. 추측은 추측이라고 표시하고, 재현 입력과 기대 결과를 함께 적는다.
4. **문체**: 리뷰 본문의 문장은 표준어 존댓말(`~합니다`, `~입니다`, `~습니다`)로 쓴다. `~한다`·`~이다` 같은 평서체, 방언, 줄임말, 인터넷 말투는 쓰지 않는다. 형식 요소(첫 줄 마커, 섹션 제목, `[치명]`·`[중요]`·`[제안]` 태그, `판정:` 줄)는 아래 고정 형식을 그대로 둔다.
   - 예: `- [중요] 파일:줄 빈 목록이 들어오면 예외가 발생합니다 — 실패 시나리오 / 제안: 빈 목록을 먼저 확인합니다.`
   - 예: `- 확인: 타입 체크와 테스트가 통과했습니다. / 못 함: 실기기 동작은 확인하지 못했습니다.`

## 영역별 확인 사항
- **WebView·URL 정책** (`src/features/projects/url-policy.ts`, `src/app/project/[id].tsx`)
  - 허용 호스트는 서비스 호스트와 카탈로그 `allowedHosts`뿐이다. HTTPS만 허용하고 `javascript:`·`file:`이 열리지 않아야 한다.
  - `allowedHosts`를 넓히는 변경은 범위와 이유(로그인 흐름에 필요한 호스트인지)를 확인한다. 와일드카드·포트·경로는 허용하지 않는다.
- **카탈로그** (`catalog/projects.json`, `catalog.ts`)
  - 새 URL이 실제로 응답하는지, `id`가 레포 이름과 같은지, 중복이 없는지. 원격 JSON은 신뢰할 수 없는 입력이다.
- **알림** (`src/features/notifications`, `.github/workflows/notify-*.yml`)
  - 이벤트 계약(`version=1`)을 깨지 않는지. 알림 실패가 배포를 막지 않는지(재사용 워크플로는 항상 성공으로 끝남).
  - 취소·skip이 성공 알림으로 나가지 않는지, 호출 레포의 SHA 갱신이 필요한 변경인지.
  - Android 채널 ID 변경이 필요한 설정 변경인지(`setup.ts`의 `DEPLOYMENT_CHANNEL`과 워크플로 `channelId`가 일치해야 함).
- **워크플로·시크릿**
  - 입력은 환경변수로만 셸에 전달하는지(셸 인젝션 방지). 토큰·시크릿이 로그, 코드, 문서에 나오지 않는지.
  - 외부 액션과 재사용 워크플로 참조가 고정돼 있는지(`@<커밋 SHA>` 또는 버전).
- **앱 일반**: 로딩·오류·재시도·뒤로 가기·접근성·safe area. Expo 패키지는 `npx expo install`로 추가했는지, lockfile이 하나인지.

## 심각도
- **치명**: 데이터 손실, 시크릿·토큰 노출, 보안 경계 우회, 앱 크래시·배포 장애를 일으키는 문제. 반드시 수정한다.
- **중요**: 정확성 버그, 알림·WebView·카탈로그 동작 훼손, 검증 누락, 요구사항 미충족. 병합 전에 수정한다.
- **제안**: 가독성·구조·성능 개선, 선택 사항. 병합을 막지 않는다.
- 확인하지 못한 추측은 한 단계 낮춘다. 근거(파일:줄, 재현 입력)가 있는 지적만 치명·중요로 올린다.

## 보고 형식 (게이트가 읽는 형식)
리뷰 본문은 아래 형식을 그대로 따른다. 첫 줄 마커와 `판정:` 줄이 없으면 게이트가 리뷰로 인정하지 않는다.
```
<!-- code-review -->
## 코드 리뷰 (`<HEAD 커밋 7자>`)
### 치명
- [치명] `파일:줄` 문제 — 실패 시나리오 / 제안
### 중요
- [중요] `파일:줄` 문제 — 실패 시나리오 / 제안
### 제안
- [제안] `파일:줄` 내용
### 확인한 것 / 못 한 것
- 확인: … / 못 함: …
판정: 승인 | 수정 필요
```
- 지적 줄은 반드시 `- [치명]`, `- [중요]`, `- [제안]`으로 시작한다(게이트가 이 줄을 센다). 해당 단계에 지적이 없으면 그 섹션을 생략한다.
- 치명·중요가 하나라도 있으면 `판정: 수정 필요`, 없으면 `판정: 승인`.
- 지적이 없으면 "지적 없음"과 확인한 범위를 적고 `판정: 승인`.

## 리뷰 남기는 방법
1. 커밋을 푸시한 뒤 리뷰 본문을 위 형식으로 파일에 쓴다. 리뷰는 남긴 시점의 PR HEAD 커밋에 연결되므로 **푸시 후에 남긴다.**
2. `bash .github/scripts/post-review.sh <PR번호> <본문 파일>`로 남긴다. 이 스크립트가 리뷰를 게시하고, HEAD의 CI 실행이 끝나면 `check`를 **재실행**해 게이트를 다시 평가한다.
3. 치명·중요를 고쳐 푸시했다면 새 HEAD 기준으로 리뷰를 **다시** 남긴다(이전 리뷰는 무효).
- 리뷰만 직접 남기고(`gh pr review`) 재실행을 빼면 게이트가 갱신되지 않아 병합이 막힌다.
